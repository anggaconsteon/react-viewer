# addToEvent — Flutter Dev Spec

**Status:** v0.2 (initial draft, 2026-06-01)
**Audience:** Flutter engineers implementing the event ledger pipeline
**Related artifacts:**
- `file/addToEvent guide.txt` — DSL spec (source of truth)
- `file/addToTable guide.txt` — sibling DSL (positional)
- `memory/reference_addToEvent_pattern.md` — design memory

---

## 1. Overview

`addToEvent` is a new DSL pattern that appends one document per user action into the event ledger (Firestore + spreadsheet). It is a **keyed sibling** of the existing `addToTable` pattern.

**Why a new pattern?**
`addToTable` is positional — every field slot is `<N>`, must be filled in order. Sparse data isn't supported, and inserting a new field shifts every downstream index.

`addToEvent` is keyed by short char-codes (`ty`, `t`, `cv`, …). Field order is free, omissions stay empty, and adding a field never breaks existing pages.

**Scope of this doc:**
- Parser behavior the Flutter client must implement
- Output shape (Firestore document)
- Auto-derived fields (`et`, `p`, `ev`, `ld`) and where each comes from
- Test vectors

## 2. End-to-end flow (parallel to addToTable)

```
[Widget JSON in op1Screen]
   │ contains: "addToEvent": "<raw string>"
   ▼
[Flutter widget renders form]
   │ user fills form fields
   ▼
[Submit handler]
   │ reads addToEvent string template
   ▼
[Parser]
   │ 1. detect header (addToTable vs addToEvent)
   │ 2. branch to keyed-mode for addToEvent
   │ 3. split by ⭘ → split by ◼ → build Map
   │ 4. resolve tokens (◀▶ system stream, ◁N▷ form input)
   ▼
[Output: Map<String, dynamic>]
   │
   ├─► Firestore write — document into target collection
   │   (path derived from line 1 of the string, e.g. vtl.event-report-incident)
   │
   └─► Event tab write — push col A/B/C to Google Sheet
       (col D is computed by an op1-sheet formula; Flutter does NOT generate it)
```

The flow is intentionally identical to `addToTable`. The only difference is which parser branch runs and the output shape.

## 3. DSL syntax (recap)

```
addToEvent":
<collection-name>          ← line 1, user-defined (e.g. vtl.event-report-incident)
⭘r◼4320                    ← retention minutes
⭘tablevid◼<vid>            ← optional, convention: right after r
⭘ty◼<event-type>           ← event type (semantic, matches `flag` in addToTable)
⭘t◼◀N|T7|epoch▶            ← timestamp (epoch ms)
⭘ts◼◀N|T7|Ddd MMM yyyy HH:mm:ss▶   ← timestamp string
⭘cv◼<creator-vid>          ← e.g. 87544551624342
⭘cn◼<creator-name>         ← e.g. Bob Kosasih
⭘sv◼◁8▷                    ← form field 8 (right-side / user input)
⭘d◼◁3▷                     ← form field 3
...
```

Multi-doc inserts use `◆` between blocks (same as `addToTable`).

**Tokens (shared with `addToTable`):**

| Token | Meaning |
|-------|---------|
| `◀N|T7|format▶` | Left-side stream value from system context (timestamp, gps, etc.). `T7` = timezone Asia/Jakarta. `format` = epoch / `Ddd MMM yyyy HH:mm` / etc. |
| `◁N▷` | Right-side form field N (raw user input from the page). |
| `◁N|T7|format▷` | Right-side form field N, formatted. |
| literal | Bake the value as-is. |

## 4. Field dictionary

The parser MUST treat the following as the canonical character codes. Unknown char-codes are NOT errors — they pass through into the output Map as-is (forward-compatible).

### 4.1 Metadata

| Char | Meaning | Source |
|------|---------|--------|
| `r` | Retention minutes (e.g. `4320` = 72h) | DSL literal |
| `fc` | Ledger code (free label) | DSL literal |
| `tablevid` | Explicit collection VID | DSL literal |
| `et` | Event time (epoch ms) — **Event tab col A** | Auto-generated client-side (see §6) |
| `p` | Page / route name — **Event tab col B** | Auto-generated client-side (see §6) |
| `ev` | Event content (raw payload) — **Event tab col C** | Auto-generated client-side (see §6) |
| `ld` | Ledger transform — **Event tab col D** | NOT generated by Flutter. Computed by spreadsheet formula in `op1` tab. |

### 4.2 Event content

| Char | Meaning |
|------|---------|
| `ty` | Event type (e.g. `report-incident`, `attendance-check-in`) |
| `t` | Time (epoch ms) |
| `ts` | Time string (formatted) |
| `ln` | Location name |
| `lq` | QR ID |
| `i` | Image URL |
| `d` | Description |
| `cv` | Creator VID (user VID) |
| `cn` | Creator name |

| `sv` | Site VID |
| `sn` | Site name |
| `cl` | Checklist |
| `rf` | Ref ID — bridges event log to main table and links approval chains. Value is author-defined: `<no_request>` (system-injected), `◁N▷` (form field), literal, or omit. See §6.5. |

|------|---------|

## 5. Parser spec

### 5.1 Input

A raw string starting with `addToEvent":` followed by a newline-or-inline block of fields. The first non-header line is the **collection name** (no `⭘` prefix). Subsequent lines are key/value pairs separated by `◼` and prefixed by `⭘`.

### 5.2 Algorithm

```dart
Map<String, dynamic> parseAddToEvent(String raw) {
  // 1. Strip header "addToEvent":
  final body = raw.replaceFirst(RegExp(r'^addToEvent\"?:\s*'), '');

  // 2. Split on ◆ for multi-doc — out of scope here, see §7
  final docBlock = body.split('◆').first;

  // 3. Split on ⭘
  final parts = docBlock.split('⭘').map((s) => s.trim()).where((s) => s.isNotEmpty).toList();

  // 4. First part = collection name
  final collectionName = parts.first;

  // 5. Remaining parts = key◼value pairs
  final result = <String, dynamic>{
    '_collection': collectionName,
  };
  for (final part in parts.skip(1)) {
    final eq = part.indexOf('◼');
    if (eq < 0) continue; // malformed, skip silently
    final key = part.substring(0, eq).trim();
    final rawValue = part.substring(eq + 1);
    result[key] = resolveTokens(rawValue);
  }
  return result;
}
```

### 5.3 Sparse semantics

- A char-code that does NOT appear in the source string is NOT inserted into the output Map.
- **However**, when writing to Firestore, the writer SHOULD pre-fill every dictionary char-code as `""` (empty string), then overwrite the present ones. This produces the "key exists, value empty" shape shown in the reference Firestore screenshot.

```dart
final fullDoc = {
  for (final code in canonicalFieldCodes) code: '',
  ...parseResult,
};
firestore.collection(collectionName).add(fullDoc);
```

This rule applies only at the Firestore-write boundary, not inside the parser.

### 5.4 No validation

There are no required-field checks. Missing `ty`/`t`/`ts` is allowed at the parser level. (Backend / downstream consumers are responsible if they require specific keys.)

### 5.5 Unknown char-codes

Unknown char-codes pass through unchanged into the output Map. They don't throw. This keeps the dictionary forward-compatible — when a new code is added, deployed clients keep working.

### 5.6 Unified parser

The same entry function should accept BOTH `addToTable` and `addToEvent` strings and branch on header:

```dart
dynamic parsePayload(String raw) {
  if (raw.startsWith('addToTable')) return parseAddToTable(raw);
  if (raw.startsWith('addToEvent')) return parseAddToEvent(raw);
  throw FormatException('Unknown payload header');
}
```

Token resolution (`resolveTokens`) is shared between both.

## 6. Auto-derived fields — `et`, `p`, `ev`, `ld`

These four are NOT user-defined in the DSL string. They correspond to the four leftmost columns of the `Event` spreadsheet tab.

### 6.1 What each one represents

| Col | Header in `Event` tab | DSL char | What it holds |
|-----|----------------------|----------|---------------|
| A | Time | `et` | Epoch ms when event landed |
| B | Route | `p` | Route / page name |
| C | Data | `ev` | Raw event content (`◆`-delimited payload) |
| D | (Stored / transformed) | `ld` | `◼` / `◻` / `☆` delimited transform of C |

### 6.2 Generation responsibility — DEV ANALYSIS

| Field | Where it is generated | Notes for Flutter dev |
|-------|----------------------|------------------------|
| **`et` (A)** | **Flutter, at submit time.** | `DateTime.now().toUtc().millisecondsSinceEpoch`. Push this value as col A of the Event row, and OPTIONALLY also use it as the `t` field inside the document content. The two should agree. |
| **`p` (B)** | **Flutter, at submit time.** | Take the active route name. For provider-only flows it can be the provider key (`vertikaTeknoLokacipta`). For specific page flows it should be the full page key (`vertikaTeknoLokaciptaRequestLeave`). Decide per-flow; the page widget is the closest to this information. |
| **`ev` (C)** | **Flutter, at submit time.** | This is the rendered, token-resolved addToEvent payload string ITSELF — i.e. the same body you pass to the parser, with `◀▶` and `◁▷` substituted. Send this string as-is into col C. |
| **`ld` (D)** | **Spreadsheet formula in the `op1` tab.** | Flutter does NOT generate this. After Flutter writes A/B/C, the spreadsheet's existing formula in `op1` interprets col C and produces col D. Flutter must never write col D itself. |

**Implementation suggestion:**

```dart
class EventRow {
  final int eventTimeMs;    // A
  final String routeName;   // B
  final String rawPayload;  // C
  // D is intentionally omitted — spreadsheet computes it.
}

Future<void> submitEvent({
  required String addToEventTemplate,
  required Map<int, dynamic> formFields,
}) async {
  // 1. Resolve tokens (◁N▷ → formFields[N], ◀N|...▶ → system stream)
  final resolved = resolveAllTokens(addToEventTemplate, formFields, now: DateTime.now());

  // 2. Parse into Map for Firestore
  final doc = parseAddToEvent(resolved);

  // 3. Build the EventRow for the spreadsheet
  final row = EventRow(
    eventTimeMs: DateTime.now().toUtc().millisecondsSinceEpoch,
    routeName: ModalRoute.of(context)?.settings.name ?? '',
    rawPayload: resolved.split('◆').first, // or full resolved string
  );

  // 4. Write
  await Future.wait([
    firestore.collection(doc['_collection']).add(_fillBlanks(doc)),
    sheets.appendRow('Event', [row.eventTimeMs, row.routeName, row.rawPayload]),
  ]);
}
```

### 6.3 Why split A/B/C generation between Flutter and the DSL

Flutter has the live context the DSL doesn't:
- The user's wall-clock time at submit (`et`).
- Which screen / route they were on (`p`).
- The final rendered payload AFTER token substitution (`ev`).

The DSL string is a **template**. Until tokens resolve, it has no concrete timestamp or rendered payload. Flutter is the only layer that knows.

### 6.4 Why `ld` stays in the spreadsheet

`ld` is a normalized projection of `ev` — it splits the `◆` payload into discrete `◼`/`◻`/`☆` segments, joins with profile data (name, site, provider) and computes serial-date numbers. That logic lives in the `op1` tab's formula library and is reused across all event types. Re-implementing it in Flutter would duplicate state that is already maintained centrally.

If you need `ld` on the client (rare), read it back from the spreadsheet after the formula has populated it.

## 6.5 `rf` — cross-DSL linkage

`rf` is the bridge that connects an event log entry to (a) the row in the main table that the same submit just wrote via `addToTable`, and (b) other events in the same approval chain.

### Value is author-defined

The DSL author chooses where `rf`'s value comes from. The parser does not enforce one form. Four options:

| Source | Token | Use case |
|--------|-------|----------|
| System-injected | `<no_request>` | New submit (system generates a new ref id) OR detail/approval page (system inherits from parent context). Same convention as `addToTable`. |
| Form input | `◁N▷` | User types or scans the ref id into form field N. |
| Literal | `<id-string>` | A known id is baked at template time. |
| Omit | — | The event has no linkage to a transaction (read-only or standalone). |

### Resolver responsibilities

- `<no_request>` MUST be resolved by the system to the same value the sibling `addToTable` uses in the same submit. New submits get a fresh id; detail/approval pages inherit the parent's id.
- `◁N▷` MUST be resolved from form field N like any other right-side token.
- Literal values pass through unchanged.
- When `rf` is omitted in the DSL, the parser MUST NOT inject a default. The Firestore document simply has `rf: ""` (or absent, depending on the sparse-fill policy in §5.3).

### Same-submit consistency for `<no_request>`

When `addToTable` and `addToEvent` both contain `<no_request>` in the same submit, Flutter MUST substitute them to the same value. Generate once, bind to both parsers.

```dart
final refId = systemRefIdProvider.next();
final resolvedTable = template.addToTable.replaceAll('<no_request>', refId);
final resolvedEvent = template.addToEvent.replaceAll('<no_request>', refId);
```

For approval chains, the resolver looks up the parent's ref id instead of generating a new one — but this is a substitution policy at the application layer, not a parser concern.

## 7. Multi-doc inserts

A single `addToEvent` string MAY contain multiple docs separated by `◆`. Each doc is parsed independently and written as its own Firestore document.

```
addToEvent":
vtl.event-clock-in
⭘r◼4320
⭘ty◼clock-in
⭘t◼◀2|T7|epoch▶
⭘ts◼◀2|T7|Ddd MMM yyyy HH:mm:ss▶
⭘cv◼87544551624342
◆
vtl.event-attendance-check-in
⭘r◼4320
⭘ty◼attendance-check-in
⭘t◼◀2|T7|epoch▶
⭘ts◼◀2|T7|Ddd MMM yyyy HH:mm:ss▶
⭘cv◼87544551624342
⭘ln◼BSD Tech Center #26
⭘lq◼0l114807f17536338c20fd13c3896308df116b295d
⭘i◼◁6▷
```

Writes SHOULD be batched. If the backend supports atomic batch writes (Firestore `WriteBatch`), use it. If one doc fails, fail the whole submit and surface a single error to the user — never leave the ledger in a half-written state.

## 10. Implementation checklist

- [ ] Header detector branches `addToTable` vs `addToEvent` to the right parser.
- [ ] `parseAddToEvent` returns `Map<String, dynamic>` with `_collection` key.
- [ ] Token resolver is shared with `addToTable` (no duplication).
- [ ] Multi-doc `◆` split is handled before per-doc parse.
- [ ] Firestore writer pre-fills canonical dictionary keys with `""` before merging in the parse result.
- [ ] Event-tab writer pushes only A/B/C; never touches D.
- [ ] No validation throws on missing keys or unknown char-codes.
- [ ] Multi-doc writes are batched and atomic per submit.

## 11. Open questions / future work

1. **Should `et` and `t` ever diverge?** Currently both should equal the submit timestamp. Define a rule if a flow could ever supply a backdated `t` via form input.
2. **Atomic write between Firestore and Sheets** — Sheets has no transaction primitive. If the Firestore write succeeds but the Sheets append fails (or vice versa), what is the recovery path? Suggest a retry queue or a server-side replicator.
3. **Dictionary versioning** — when char-codes are added or renamed, how does Flutter know which dictionary version a given proxy spreadsheet expects? Suggest embedding a `dict-version` cell in the spreadsheet metadata.
4. **Type coercion** — the parser currently emits everything as strings. `t` should arguably be `int`. Decide whether to coerce at parser time using the dictionary, or leave coercion to the consumer.
