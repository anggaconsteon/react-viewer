## 2. Internalize these invariants

- **Keyed, not positional.** Field name = char-code (`ty`, `t`, `cv`, …) — NOT `<N>`.
- **Sparse-by-default.** Omit a field → empty in Firestore. Never write `⭘fc◼` with empty value.
- **Append-only.** No update/delete variant. Mutations go through `updateTableRow`; new event appended with `rf` linking back.
- **Required:** `r`, `ty`, `t`, `ts` (validator skipped at parser level, but conventionally always present).
- **`et`/`p`/`ev`/`ld` are NOT Firestore doc fields.** Excluded from `canonicalEventCodes`. They are Event-tab spreadsheet columns: `et`/`p`/`ev` generated by Flutter at submit, `ld` computed by op1-sheet formula.
- **Char-code pairs:** `av`/`an` = cost-center VID/name; `sv`/`sn` = site VID/name. NO "area name" char-code.
- **`t` is int** (epoch ms). Other fields default to string.
- **`rf` value flexible:** `<no_request>` (system-injected via screenTx) / `◁N▷` (form field) / literal / omit.
- **Token semantics shared with `addToTable`:** `◀N|T7|format▶` left/system stream, `◁N▷` right/form input, literals bake as-is, `|T7|format` formats the value.
- **Per-feature char-code bloat is anti-pattern.** Keep dictionary small. Feature-specific UX fields belong in `addToTable`, not event log. Reuse `d` for free-text catch-all.

## 4. Pattern template

```
<table-name>
⭘r◼<retention-minutes>
⭘tablevid◼<vid>                        (optional, after r by convention)
⭘fc◼<ledger-code>                      (optional)
⭘ty◼<event-type>
⭘t◼◀N|T7|epoch▶
⭘ts◼◀N|T7|Ddd MMM yyyy HH:mm:ss▶
⭘cv◼<creator-vid>
⭘cn◼<creator-name>
⭘av◼<cc-vid>                           (optional)
⭘an◼<cc-name>                          (optional)
⭘sv◼◁N▷                                (site vid from form)
⭘sn◼◁N▷                                (site name from form)
⭘d◼◁N▷                                 (description / free text)
⭘i◼◁N▷                                 (image url)
⭘rf◼<no_request>                       (optional, see linkage rules)
```

## 5. When generating addToEvent strings, ask:

1. What main-table write fires alongside? (`addToTable` flag, table name)
2. What form fields exist on the page? (`◁N▷` positions)
3. Is this a ROOT submit (new transaction) or CHILD (approval / detail action)?
   - Root → omit `rf` OR `<no_request>` if system generates new id
   - Child → `<no_request>` (inherits parent rf via screenTx)
4. Is the event log purpose served by the small dictionary, or is there a real new field needed? (Default: NO new code; reuse `d`.)
